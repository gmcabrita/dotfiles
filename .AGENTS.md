## Code exploration

Use `ast-grep` for structural code searches. Use `rg` for literal text, identifiers, paths, and error messages. Use `ast-grep outline` when a file overview will help. Read only the context needed for the task.

## Implementation

When building features, build a tiny, end-to-end slice of the feature first, seek feedback, then expand out from there.

Tracer bullets comes from the Pragmatic Programmer. When building systems, you want to write code that gets you feedback as quickly as possible. Tracer bullets are small slices of functionality that go through all layers of the system, allowing you to test and validate your approach early. This helps in identifying potential issues and ensures that the overall architecture is sound before investing significant time in development.

## Task completion

## Code Quality Standards

- Write code for humans to read
- Make minimal, surgical changes
- Design for testability using "functional core, imperative shell": keep pure business logic separate from code that does IO
- Use types to prevent invalid states where the language supports this clearly. Parse and validate external inputs at boundaries.
- Keep changes limited to the task. Avoid unrelated refactoring. Add abstractions only when they simplify the required behavior. Document constraints and decisions that the code does not explain.
- Prefer hard cutovers. Do not add backward compatibility unless asked. Before making a public API, data format, or user-visible breaking change, explain the impact and obtain approval unless that change is already authorized.

## Testing

- Test behavior, not implementation details. Run checks appropriate to the change and any checks required by the repository. Repeat or expand checks only when changes, failures, or unresolved risks justify it.
- Do not weaken correct tests to obtain a pass. Report remaining failures and distinguish existing bugs from regressions caused by the change. State what was not verified.
